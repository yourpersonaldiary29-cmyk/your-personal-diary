TARGET BEHAVIOUR:
1. Offline, the lock screen shows the password form as it does online, with a one-line note "No connection: your password is checked on this device." The device-screen-lock button stays as a second way (unchanged). The "needs a connection" fallback appears only when NEITHER way exists (no device check and no password wrap on this device).
2. A correct password unlocks this device's screen only (exactly like the device check today: unlockOffline; the server session stays whatever it was; a 423 later still asks for the password to upload - that path is unchanged).
3. A wrong password shows the usual wrong-password error; after 3 wrong passwords offline, each further attempt waits with a growing delay (2 s, 4 s, 8 s ... capped at 60 s) shown in the field's error text; the counter resets on a successful unlock or a reconnection.
4. Without "Remember me" (and on the web), the password can still be used offline during the SAME run of the app (the wrap lives in memory only and dies with the page) - nothing new is written at rest. With "Remember me" in the apps, the wrap is kept at rest so that an app that was restarted without a connection can be unlocked by password too.

DESIGN (binding unless you find a real problem - then say so in openIssues and do the closest safe thing):
- New module src/offline/password-wrap.ts: makePasswordWrap(password, aok, userId) -> wrap object { v: 1, kdf: 'scrypt', N: 32768, r: 8, p: 1, salt: base64 16 random bytes, nonce: base64 12 random bytes, ct: base64 AES-256-GCM(aok, key = scrypt(utf8(password), salt, N, r, p, 32), additionalData = utf8('ypd-offline-pw-v1:' + userId)) }; openPasswordWrap(password, wrap, userId) -> the AOK bytes or null (any failure = null; never throws on wrong password). scrypt from @noble/hashes (already a dependency at 2.4.0: import { scryptAsync } from '@noble/hashes/scrypt' - the async variant with yields, so the UI does not freeze; measure the time on this PC and note it; use the same parameters as the server's kdf.ts so the offline brute-force cost equals the server-side one), AES-GCM through Web Crypto (src/offline/crypto.ts helpers; reuse randomBytes/toBase64/fromBase64/ownBytes/zero). The password string is used exactly as typed (the same string the login form sends; no normalization). Zero the AOK bytes and the derived key material as soon as possible (zero() on Uint8Arrays; CryptoKeys are non-extractable).
- Storage: meta row META.passwordWrap = 'passwordWrap' (JSON of the wrap) in the account's IndexedDB, written ONLY when the engine is persistent (apps with "Remember me"); otherwise kept in the engine's memory. Lifecycle = exactly that of meta.wrappedKey: written/refreshed whenever the engine is armed with a password in hand; deleted by every path that deletes meta.wrappedKey (purgeSensitive, purgeAccountAtRest, wipeAccount, removeWrappedKey, the no-"Remember me" start, account switch) - add it to those code paths, not to new ones; and dropped from memory on teardown.
- When is the password "in hand"? (a) login with a password (AuthContext.login -> offline.start: add an optional password argument to StartArgs, passed only on a password login, never stored anywhere else, cleared after the wrap is made); (b) a successful verifyPassword against the server (the online lock screen and the 423 upload prompt - AuthContext.verifyPassword knows the password at that moment: on success, hand it to the engine: offline.refreshPasswordWrap(password)); (c) a successful password change (the new password: find the change-password call in src/pages/settings and the API client; on success refresh the wrap with the NEW password). A cache start (app reopened with "Remember me") has no password in hand: the wrap at rest is what serves it. (d) When the server's answer to verifyPassword/login is a failure, nothing is written.
- Verification offline: offline.unlockWithPassword(password) -> 'ok' | 'wrong' | 'unavailable': reads the wrap (memory or meta), openPasswordWrap, then deriveKeys(aok, userId) and verifyKeyCheck against meta.keyCheck (or against the armed keys' check - reuse ensureKeyCheck/verifyKeyCheck; the engine is already armed, so a boolean is enough); 'unavailable' when there is no wrap. The throttle (target 3) lives in the engine (per account, in memory) so a page reload does not reset it in the same run - but a restart may (document).
