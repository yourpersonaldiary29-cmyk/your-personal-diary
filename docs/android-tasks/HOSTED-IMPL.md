11. OWNER DECISION 2026-10-18: AUTOMATIC OFFLINE MODE (new package WP-H10, after WP-H5/H6). The app detects by itself that the server is unreachable (navigator.onLine + a failed health/request), shows a non-blocking banner ("no connection - what you write will be saved to the server when the connection returns", 20 locales), lets the user keep working, and when connectivity returns it uploads what the user did, in order, exactly once, even if the app was closed in between. Scope v1: writes queued = create/update/delete entry, habit quick log/log edits, habit create/edit/archive, settings changes; reads offline = a per-account local cache of what was loaded last (recent entries, habits, today's data, calendar month, settings) + the queued changes merged in; insights, search, stats, backup/restore, exports and account management need a connection (clear message). Conflict rule: per record, the newer updatedAt wins; a server-deleted record is not resurrected by a queued edit (the user sees a one-line note). Server side: client-generated UUIDs for created records (idempotent replay: a `clientId` unique per account) and an optimistic concurrency check on updates (`If-Match`/version or updatedAt) - minimal schema change with migration and tests. Client side: the queue and cache live in IndexedDB in the app's sandbox (Android app-private storage; Windows user profile), scoped per account, encrypted with a key kept in sessionStorage/Keystore where available (design it; document the residual risk), cleared on logout and on account deletion; replay runs on reconnect, on app start and on resume with exponential backoff; the UI shows "N changes waiting" and errors per item. This applies to Windows, Android and the web UI alike (one implementation in src/). Tests: unit tests for the queue (ordering, idempotency, conflict rules), replay against the hosted server in a test, offline/online transitions in component tests. Privacy policy: mention the local cache/queue.
