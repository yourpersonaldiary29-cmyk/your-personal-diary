DESIGN TASK: cross-device sync for "Your Personal Diary" (desktop Windows app + Android app, later iOS).

OWNER REQUIREMENT (verbatim meaning, 2026-10-16): "Make sync. If the user registers with the same username and password on the phone too, it must show everything they did." It must work when the owner is NOT at home (the home internet is behind carrier-grade NAT, so the phone can never reach the PC from outside; the PC may be off). Every user of the app (not only the owner) must be able to use it. The app's promise stays: the diary content is readable only with the user's password; nobody else (including us and any cloud provider) can read it; no telemetry.

READ FIRST: docs/ANDROID-PLAN.md, ARCHITECTURE.md (storage, container format, accounts, sessions, recovery key), docs/API.md, server/src/security/{container,kdf,vault,accounts,auth-service}.ts, server/src/db/{schema,database,entries-repo,habits-repo,settings-repo}.ts, server/src/backup/backup.ts, server/src/remote/** (how optional network features are gated and audited: scripts/check-no-network.mjs), mobile/core/** (the phone core), mobile/host/**, docs/android-tasks/WP-7-8-9.md and WP-12.md (native plugin pattern), the i18n layout (20 locales).

QUESTIONS THE DESIGN MUST ANSWER WITH EVIDENCE (quote code, measure sizes):
1. Transport. Compare, with concrete pros/cons for THIS owner (non-programmer, no admin rights, CGNAT at home, wants privacy) and for ordinary users: (a) the user's own cloud storage through an official API with an app-private folder (Google Drive appDataFolder via OAuth 2.0; what the owner must create once in Google Cloud Console - an OAuth client - and what consent/verification Google requires for the drive.appdata scope, with sources from developers.google.com; how the desktop app does OAuth (loopback redirect in the system browser) and how Android does it (AppAuth/Credential Manager, Android OAuth client with the signing SHA-1); token storage; offline access; quotas); (b) a user-chosen folder synced by the user's existing cloud client (Windows OneDrive/Google Drive folder; Android Storage Access Framework tree on a Drive/OneDrive provider) - reliability of background refresh and change detection; (c) direct LAN sync between the PC and the phone on the home Wi-Fi (works at home only); (d) a relay server operated by the owner (he cannot host; CGNAT) or by us (cost, trust) - probably rejected, say why; (e) WebRTC peer-to-peer (needs signaling). Recommend one primary transport and, if cheap, a secondary one (LAN) that shares the same sync engine. Any transport must keep zero-knowledge: only ciphertext leaves the device.
2. Identity and keys. "Same username and password on both devices" must be the whole story for the user. Define how a device finds the other device's data (per Google account + username -> sync space), how the sync payload is encrypted so that any device with the password can open it (the existing container format already stores the scrypt salt in its header - reuse it or derive a dedicated sync key? what about password changes on one device while the other is offline? what about the device-wrapped recovery key - it must never leave the device), and what happens with a wrong password (no access, clear message), a renamed account, a deleted account, two different people with the same username on two different Google accounts (no clash).
3. Merge. Today ids are per-device integers (check schema.ts: entries, habits, habit_logs, settings, insights notes...). Design a correct merge: global ids (UUID column + migration, keep integer ids for the UI), per-record updatedAt with a device clock caveat (use Lamport/hybrid logical clocks or per-record version vectors? justify), tombstones for deletions, last-writer-wins per record (or per field for entries?), and the rule for the same entry edited on both devices while offline (LWW + keep the loser as a visible "conflict copy"? recommend one with the owner's simplicity in mind). Habit logs keyed by (habit uid, date) merge by max/latest. Settings merge (language per device vs per account). Insights are derived, never synced. The engine must be deterministic, idempotent, and run identically in Node (desktop) and in the worker (phone) from the same TypeScript in server/src.
4. Protocol on the transport: per-device encrypted snapshot files vs an append-only encrypted change log (sizes for a 5-year diary: estimate from the demo data: 120 entries = 53 KB container), how often to sync (on app start, after changes with a debounce, manually, on resume), conflict-free without locks, partial failure and resume, clock skew, a device that was offline for months, storage quota, and what the user sees (Settings card "Sync between my devices": connect/disconnect, status, last sync time, devices list, "Sync now", errors in plain words, all in 20 languages).
5. First-use flows written as numbered user steps: (i) owner already has the PC diary, installs the phone app, registers with the same username+password, turns on sync and connects Google -> the PC data appears; (ii) new user starts on the phone, later installs on a PC; (iii) a user who never wants sync (nothing changes, no account prompts); (iv) password change; (v) device lost (revoke from the other device; Google account security).
6. Security review of the design: threat model (cloud provider, someone with the Google account but not the password, someone with the PC profile, replay/rollback of old snapshots, downgrade of the format, malicious snapshot content -> schema guard), rate of scrypt operations, and the audit rule to add to scripts/check-no-network.mjs (which hosts the new sync module may contact, only when the user enabled sync).
7. Work packages for implementation (file ownership, dependencies, which need the phone, which need the owner's Google Cloud client id), with acceptance criteria and tests (property tests for the merge: commutative, idempotent, convergent across 3 devices with random offline edits; compat: PC snapshot opened on the phone core and back). Keep desktop behaviour unchanged for users who do not enable sync.
