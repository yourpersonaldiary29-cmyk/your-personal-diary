WP-7 FILES
- Saving a backup or an export on the phone: the UI gets the bytes from the core as today (blob download path). On the phone, instead of an <a download>, offer "Save to device" (Android Storage Access Framework: ACTION_CREATE_DOCUMENT with the suggested file name and MIME type; a small local plugin mobile/plugins/diary-files in Java, no storage permission needed) and "Share" (@capacitor/share with a file in the app cache directory; delete the cache file afterwards). Large files: pass data in chunks, never one huge base64 string that could freeze the WebView (measure a 10 MB backup).
- Restoring: the existing <input type="file"> picker must work in the WebView (verify how Capacitor handles it; if not reliable use ACTION_OPEN_DOCUMENT in the plugin). - Hardware/gesture Back: App.addListener('backButton') -> handleBack() from src/utils/back-handler.ts ('closed-dialog' | 'navigated' | 'exit' -> App.minimizeApp()). Predictive back on Android 14+ must not exit while a dialog is open.
- Biometric unlock of the LOCK SCREEN only (never a replacement for the account password at login or for password confirmations): setting "Unlock with fingerprint/face" in the Security card. Design it honestly and securely: the lock is a server-side session lock that needs the account password to unlock (verify-password). To unlock with biometrics the app needs a secret that proves the user unlocked before: store a random unlock token, created by the core when the user enables the setting with their password, in the Android Keystore bound to biometric authentication (BiometricPrompt with a CryptoObject; key invalidated on new enrolment), and let the core accept that token for unlocking THIS session only (a new core control/endpoint is needed: describe the exact contract in notesForOthers and implement the host/UI/native side; if the core part cannot be done inside your ownership, leave the setting hidden behind a feature flag and say so - do not fake it by remembering the password).
