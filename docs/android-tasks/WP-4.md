GOAL: server/src uses synchronous fs calls for small registry files and fs.promises for the diary files. You build:

1. The fs facade (mobile/core/vfs/node-fs.ts, re-exported by mobile/core/shims/fs.ts as default + named exports), covering exactly what server/src uses (re-check with grep; outside remote/**, mail/node-transport.ts, middleware/host-check.ts, server.ts, index.ts):
   sync: existsSync, readFileSync (utf8 string or Buffer), writeFileSync (string|Buffer, options incl. mode ignored), mkdirSync ({recursive}), renameSync, statSync (size, mtime, isFile/isDirectory), rmSync ({force, recursive}), openSync/writeSync/fsyncSync/closeSync (used for an fsync-after-write pattern - make them work on the mirror), readdirSync if used;
   promises: readFile, open (FileHandle with writeFile/sync/close as used by security/vault.ts), rename, rm, mkdir, access;
   errors: Node-style Error objects with .code ('ENOENT', 'EEXIST', 'EISDIR', 'ENOTDIR', 'EACCES') and messages like Node, because server code branches on err.code.
   Paths are virtual posix paths (/data/accounts.json, /data/users/<id>.mpd, /assets/fonts/...).
2. The mirror: all files under /data are preloaded into memory at boot (boot(): Promise<void> lists and reads through the storage backend); sync reads/writes hit memory immediately; every mutation queues a durable native write in order (write-behind queue per file, atomic: write <name>.tmp-<n> then rename over the target; deletes and renames replayed in order). drain(): Promise<void> resolves when everything queued so far is durable - the core calls it before answering a request (WP-5) and on app pause. Concurrent writes to one file keep their order; a failed native write surfaces on drain() and on the next operation of that file (EIO) and is logged.
   Large files: users/<id>.mpd can be several MB - keep them in the mirror too (simple and correct first; note the memory cost) unless you can show a cleaner design with tests.
   Read-only assets (/assets/**: sql-wasm.wasm, fonts) come from a separate asset provider (bytes fetched by the host from the APK web assets and transferred); expose registerAsset(path, bytes) and make readFileSync/existsSync/statSync see them.
3. Memory-only areas (plan 3.3): nothing under a path registered with markVolatile(prefix) is ever sent to the backend (the guest diary lives in the server's own memory already, but keep this hook for safety) - with a test.
4. Storage backends behind one interface (mobile/shared/storage-protocol.ts: list(dir), read(path) -> bytes, write(path, bytes), rename(from, to), remove(path), mkdir(path), stat(path)):
